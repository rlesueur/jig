An always-on AI agent.
On your own machine.

Jig is a personal agent that keeps working while you are away, using the local model of your choice. Its memory, rules, audit trail and secrets stay on your machine, in files you can inspect and edit.

What Jig does

Jig is under active development. These parts are in the code today; voice and messaging channels are on the roadmap.

  • Always on

    A heartbeat scheduler runs schedules and queued tasks, breaks goals into tasks, and resumes interrupted runs from their last checkpoint after a restart.

  • Background research

    Proactive work runs in a read-only research mode: it can read permitted sources and write private notes, but cannot change files, send anything or act.

  • Memory you can see

    Every memory can be listed, searched, edited and truly forgotten through the API. Nothing is hidden in a vendor's cloud.

  • An audit trail you own

    Tool calls, policy decisions, reviews, approvals and vault use go to a local, append-only audit log in SQLite.

  • Sandboxed tools

    File tools are confined to a per-agent folder. An optional hardened Docker container adds code execution and a headless browser behind a gated egress proxy.

  • Vision, if your model has it

    Image input works with any vision-capable model. Jig checks at start-up that the model can really see, and refuses to start if it cannot.

  • A face for the agent

    The runtime streams its state over WebSocket and server-sent events, so the avatar shows at a glance whether Jig is idle, working or waiting for you.

  • HTTP API and CLI

    Chat, goals, tasks, schedules, approvals, rules, memory, audit and vault are all available locally through a documented API and the jig command.

Safety model

Safety is enforced in code, at the tool level. The prompt describes the rules but cannot loosen them. Every tool call passes through one gate, in this order:

  1. Schema. The tool must exist and its arguments must match its JSON schema.
  2. Mode. Each tool is tagged read, private write or side effect. Research mode is never offered side-effecting tools, and the gate refuses them even if the model tries.
  3. Core rules. Hard-coded and stricter-only: no credential changes, secrets only for their allowed tools, no outbound calls to localhost or the local network, and human-only actions always need you.
  4. Your rules. Allow, ask or block per tool, optionally matched on an argument such as a URL.
  5. The Sentinel. A separate model call with no tools reviews every outbound or side-effecting action. It never sees the agent's conversation, so injected web content cannot address it. A deny is final.
  6. Approvals. When a human is needed the task pauses, and resumes as soon as you approve or deny it.
  7. Vault. Tools use secrets by reference. Values are inserted only when the tool runs and are redacted from results, so the model never sees them.

Limits. The safety model is under active development and has not been independently audited. The default directory sandbox is a folder jail, not an operating-system sandbox; use the container backend for code and browsing. Please report weaknesses through the security policy.

Bring your own local model

Jig is model-agnostic. The endpoint, model name and sampling settings all come from config, and nothing in the code assumes a particular model or prompt format.

Compatible servers

Any OpenAI-compatible endpoint with tool calling, for example:

  • llama.cpp, including forks
  • Ollama
  • LM Studio
  • vLLM

Example profiles for each are in profiles/.

Built for local models. If you want a cloud model, OpenAI, OpenRouter, Anthropic and Gemini work too, only after you explicitly consent, and the safety checker can stay local.

Minimum capabilities

  • Reliable native tool calling with well-formed JSON arguments
  • JSON-schema structured output
  • A context of 32K tokens or more (advisable)
  • Decent instruction following

At start-up Jig makes a real tool call and a real structured-output request against your model, and refuses to start if either fails.

One tested set-up

Jig was developed against a 27B-class model on llama.cpp, at about 125 tokens a second on a single RTX 5090.

That is one example, not a requirement. Use whatever capable model your hardware runs well.

Quick start

You need Python 3.11 or newer and a local OpenAI-compatible server with a tool-capable model.

Windows (PowerShell)

git clone https://github.com/rlesueur/jig.git
cd jig
python -m venv .venv
.\.venv\Scripts\python -m pip install -e .
# Point jig.toml (or a profile) at your server, then:
.\.venv\Scripts\jig health
.\.venv\Scripts\jig serve
.\.venv\Scripts\jig chat --url http://127.0.0.1:8766

macOS and Linux

git clone https://github.com/rlesueur/jig.git
cd jig
python3 -m venv .venv
.venv/bin/python -m pip install -e .
# Point jig.toml (or a profile) at your server, then:
.venv/bin/jig health
.venv/bin/jig serve
.venv/bin/jig chat --url http://127.0.0.1:8766

Use a profile with jig --config profiles/ollama.toml serve. The README covers configuration, the API, tests and the container sandbox.
